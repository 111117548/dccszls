# 旧版 `ai-group-wxapp-v45.zip` 源码审阅

审阅日期：2026-07-14  
结论：有可借鉴的结构和界面内容，但没有值得直接导入的真实数据；不建议整包合并。

## 1. 包内内容

- 32 个实际文件，21 个 JavaScript 文件均通过 `node --check` 语法检查。
- 一个聊天页及侧边状态面板。
- 两个云函数：模型代理、和风天气代理。
- 角色、角色状态、Prompt、Director、GroupState、Priority、Topic、短期/长期记忆、位置、天气、世界变化和 Opportunity 模块。
- 没有云数据库读写代码。
- 没有聊天记录导出、用户记忆数据、POI 数据集、新闻、交通或天气历史。
- 没有图片、头像或其他可复用美术资产。

## 2. 必须立即处理的安全问题

### S1：模型 API 密钥已写入源码

`app.js` 中存在一个硬编码的 DeepSeek API 密钥。该密钥已经进入压缩包，应视为泄露：

1. 立即在模型供应商控制台吊销。
2. 检查调用量和账单是否异常。
3. 新密钥只能存放在服务端密钥管理或云函数环境变量中。
4. 不要把旧密钥复制到当前项目。

本文不记录密钥原文。

### S2：客户端收集并保存供应商密钥

旧聊天页允许用户输入模型和天气 API Key，并保存到小程序本地存储，再传给云函数。这个模式不适合正式产品：客户端包、调试器、日志和请求链路都会扩大泄露面。

### S3：天气云函数把完整请求 URL 写入日志

旧实现把含天气 Key 的查询 URL输出到云函数日志，可能造成二次泄露。新实现必须对 URL 查询参数脱敏。

### S4：云函数缺少服务端安全边界

- 模型云函数缺少用户鉴权、频率限制、消息长度限制、内容安全和成本上限。
- 天气云函数接受客户端提供的 API Host，扩大了外部请求滥用风险。
- `project.private.config.json` 也被打进压缩包，不应作为可分发源码的一部分。

## 3. 可以吸收的数据结构和设计

### A. 角色运行时字段

旧版已有以下概念：

- `energy`
- `socialNeed`
- `mood`
- `activity`
- `online / lurkMode`
- `lastSpeakTime`
- `speakCount`
- `interests`
- `lastTopic`
- 角色间关系映射

这些字段与新基线方向接近，可作为数据模型检查清单。当前项目已经实现了其中一部分；后续可补充 `activity`、关系状态和兴趣恢复，但不直接复制旧对象。

### B. 世界状态字段

旧版 `WorldEngine` 已划分：

- location：国家、省、市、区、地址、当前地点、附近 POI
- weather：天气、温度、体感、湿度、风、预警
- time：时段、星期、节日
- environment：餐饮、景点、交通、道路
- user：活动、上次移动、位置来源

这个分类可用于校验阶段 2 的接口字段。不过旧版大多只是空占位，不是实际数据。

### C. 状态面板 UI

旧聊天页侧边栏包含：

- 世界状态
- 群能量与情绪（旧版已有设计；全局群能量已由 ADR-015 删除）
- 当前话题和阶段
- 角色状态
- 群记忆

这套信息架构有参考价值。“世界状态”继续作为用户功能；角色兴趣、Topic 细节和调度原因仅适合开发调试。旧版群能量不再保留，见 ADR-015。

### D. 记忆分类

旧长期记忆使用 `preference / visited / dislike / important` 分类；短期记忆使用消息和事件列表。这些分类可以作为 V5 记忆设计输入，但 V4.5 按冻结决策不启用自动长期记忆。

### E. 云函数分层

“小程序客户端 → 云函数 → 外部数据源”的方向正确，可以保留服务端代理这一架构思想；具体云函数必须重写。

## 4. 只能参考、不能直接迁移的模块

| 旧模块 | 可参考 | 不能直接迁移的原因 |
|---|---|---|
| `CharacterState` | 状态字段、兴趣消耗/恢复 | 情绪和活动基本不更新；状态无持久化和用户隔离 |
| `GroupState` | 用户加能量、AI 消耗能量 | 没有 90 分强制降温、消息预算和不可变状态 |
| `PriorityEngine` | 基础关键词分类 | 天气和位置被混为 `LOCATION_QUERY`；缺少多种冻结意图和安全优先级 |
| `TopicEngine` | 生命周期、类型冷却 | 固定锁定 20 分钟，违反动态解锁决策；冷却从话题开始时计算 |
| `ConversationDirector` | 连续 AI 上限、兴趣选人 | 重大世界变化会越过用户锁；没有标准 `DirectorDecision` 和未读预算 |
| `WorldChangeEngine` | 前后快照比较 | 不看定位精度、证据、有效期和滞回，GPS 漂移可能触发跨城 |
| `OpportunityEngine` | 从变化生成机会 | 没有 ID、confidence、expiresAt、evidence；饭点会机械制造话题 |
| `ShortMemory` | 24 小时 TTL 思路 | 整包统一过期而非逐条过期；缺少来源、删除联动和敏感级别 |
| `LongMemory` | 分类概念 | 关键词命中就保存用户原话，容易误记、过度收集；V4.5 明确不做 |
| `PromptBuilder` | 角色卡/世界/记忆分段 | 无证据白名单；把位置直接声明为真实 GPS；上下文重复、成本高 |
| `LLMService` | 服务端调用方向 | 每名角色单独调用、纯文本输出、无 schema、无安全和成本遥测 |
| 聊天页 | 气泡、输入、正在输入、侧栏 | 单文件 500 行、配置与业务耦合、无群列表、无持续 AI 标识 |

## 5. 与冻结需求直接冲突的旧逻辑

1. 使用路飞、五条悟、林黛玉、白胡子、赤犬等现有角色及经典表达，违反原创角色决策。
2. 页面空闲定时器会在没有世界变化时，从饭点、天气或日常文本中随机挑话题，违反“无事沉默”。
3. Opportunity Engine 因时间段变化生成吃饭话题，容易重复触发食物讨论。
4. Topic 固定锁 20 分钟，冻结需求要求根据用户活跃动态解除。
5. 重大世界变化在 Director 中先于用户话题锁判断，可能打断用户问题。
6. 用户每次发言固定选择 2—3 名角色，不能自然只由一人回答。
7. 每位角色单独请求一次模型，成本和延迟会接近成倍增加。
8. 模型失败时使用高度刻板且重复的角色台词，会重新引入“总说吃饭/总说最强/总是伤感”的问题。
9. 位置结果没有 accuracy、采集时间和证据有效期；天气只到城市，无法满足街道/详细地点。
10. 没有小时、三小时、每日消息预算，也没有未读 30 条硬上限。

## 6. 推荐迁移方式

不把旧文件复制进当前 `miniprogram/`。按下列映射吸收信息：

| 旧内容 | 当前/未来落点 | 操作 |
|---|---|---|
| 角色状态字段 | 当前 `core/types.ts` 及未来角色仓储 | 按原创角色重新建模 |
| 世界五维字段 | 阶段 2 `WorldSnapshot` | 只补缺失字段，必须包裹 evidence |
| 世界变化测试场景 | 当前 `world-change.ts` 测试 | 增加天气预警、区县变化和证据过期用例 |
| 侧边状态面板 | 当前世界状态页 + 开发调试页 | 重做，不复制旧单页代码 |
| 短期记忆 TTL | 阶段 4 L2 Memory | 改为逐条 TTL、来源和删除联动 |
| 云函数代理 | 阶段 2 服务端适配层 | 使用环境变量、鉴权、限流、脱敏日志重写 |
| 角色兴趣和关系矩阵 | 原创角色卡 v1 | 只保留抽象维度，不保留角色名和台词 |

## 7. 最终判断

这个旧包值得作为“需求反例 + 字段清单 + UI 参考”，不值得作为当前项目的代码底座。

当前已经实现的 TypeScript 规则核心在用户优先、证据约束、GPS 漂移、防刷屏和批量角色轮次方面更符合冻结基线。后续阶段最值得从旧包吸收的是：世界面板的信息密度、角色状态字段、时间段划分、记忆分类，以及 CloudBase 调用链的经验；其余应按新架构重写。
