## 1. 目标

本规范解决“用户说一句，AI 回答一段，然后对话立即死亡”的机械节奏，同时允许角色：

- 直接回应用户，而不是只等待明确问题；
- 对用户的陈述、情绪和行动分享观点或相关经历；
- 围绕同一主题彼此接话、追问、反对、补充和收尾；
- 在有合格动机时主动分享自己的故事；
- 在用户未说话时形成短小、有意义的角色间对话；
- 在没有新增价值时自然保持安静。

活人感不等于增加消息数量。目标是让每次开口都有动机、每条消息都给下一位参与者留下可以接住的内容，同时保留沉默。

## 2. 基本单位

系统必须区分以下概念，不得继续用一个 `maxMessages` 同时代表所有层级：

| 单位 | 定义 | 默认限制 |
|---|---|---|
| 气泡 Bubble | 界面显示的一条短消息，通常只表达一个主要意思 | 单个角色回合 1—2 个 |
| 角色回合 Character Turn | 一个角色为完成一个动机所进行的一次表达 | 可包含 1—2 个相关气泡 |
| 群聊轮次 Group Round | 围绕同一触发和话题形成的一组角色回合 | 1—3 个 AI 气泡，特殊安全消息除外 |
| 自主轮次 Autonomous Round | 没有新用户消息、由合格角色机会发起的群聊轮次 | 2—3 个 AI 气泡 |
| 待发送消息 Pending Message | 已规划但尚未显示的可取消消息 | 用户发言时必须取消低优先级项 |

同一角色可以连续发送两个气泡，但必须属于同一个表达动机，第二条只能用于补充、修正、情绪延伸或自然断句。禁止把长文机械切碎，也禁止连续三个同角色气泡。

## 3. 四种交流模式

### 3.1 用户驱动对话

适用于用户提问、请求、陈述、表达情绪或分享行动。

推荐链路：

`用户 → 首答角色直接处理主要意图 → 可选补充或相关故事 → 可选其他角色接话 → 交还用户或自然结束`

第一条 AI 消息必须直接处理用户的主要意图。角色分享经历不能挤占首答，也不能把话题转成角色自我展示。

### 3.2 用户话题的延迟追聊

即时回应结束后，如果最后一条没有用明确问题把发言权交还用户，并且仍存在一个未展开的新角度，可以在约 9 秒的自然停顿后追加一次角色间追聊：

`角色 B 接住上一位角色的具体内容 → 可选角色 C 补充不同角度 → 停止并等待用户`

每条用户消息最多触发一次追聊，每次 1—2 个气泡。用户开始输入、发送新消息、离开页面或旧轮次过期时必须取消。延迟计时器只负责安排检查；真正的发言理由必须是当前未结束话题和前一条消息中仍可展开的内容。

### 3.3 角色相关分享

用户内容与某个角色的固定背景、群内共同经历、虚拟生活片段或明确兴趣高度相关时，该角色可以分享一小段故事。

故事必须满足：

- 能解释角色的观点、情绪或建议；
- 与当前话题存在明确语义连接；
- 只披露当前对话需要的一小部分；
- 不编造现实世界事实或用户共同经历；
- 不要求每次都用故事证明人格。

### 3.4 角色自主对话

用户没有新消息时，合格的角色机会可以形成短对话：

`角色 A 发起 → 角色 B 回应具体内容 → A 补充或角色 C 收尾 → 安静`

自主对话不是随机事件生成，也不能只是为了制造未读。发起内容必须来自角色合同、故事账本、真实群内历史、未完成话题或有效现实机会。

## 4. 优先级与打断

从高到低：

1. 安全事件和高风险求助。
2. 用户新消息。
3. 用户尚未回答完成的问题或请求。
4. 当前轮次中对用户的必要补充。
5. 当前角色间对话的必要收尾。
6. 合格的角色故事分享。
7. 合格的角色自主对话。

用户必须能够在“正在输入”和消息队列播放期间继续发送。收到用户新消息时：

- 立即取消尚未发送的可选角色消息；
- 保留已经显示的消息；
- 必要安全消息可以继续，其他旧轮次不得抢回话题；
- 新消息重新进入意图识别、Topic 和 Director；
- 取消动作不得被表现为角色突然删除已发出的消息。

## 5. 用户驱动轮次的节奏

### 5.1 阶段

1. **接收**：立即显示用户消息和合理的“正在输入”。
2. **首答**：最合适的角色直接回应核心意图。
3. **深化**：可由首答角色补充第二个短气泡，或由另一角色补充、反对、安慰。
4. **社交反应**：只有存在关系价值或新观点时，第三个气泡才出现。
5. **交还或结束**：留出可接的话头，或在内容已完整时自然沉默。
6. **可选延迟追聊**：即时轮次结束约 9 秒后，另一角色可接住上一条具体内容形成一次 1—2 气泡的追聊；每条用户消息最多一次。

### 5.2 参与人数目标

以下是长期统计目标，不是每轮随机强制：

| 参与结构 | 推荐占比 |
|---|---:|
| 1 个角色 | 40% |
| 2 个角色 | 45% |
| 3 个角色 | 15% |

同一即时轮次仍遵守 AI 连续气泡硬上限 3。延迟追聊属于新的短轮次，必须与即时轮次存在自然停顿且最多 2 个气泡。角色数量与气泡数量不等价：一个角色发送两个相关短气泡，也可能构成完整轮次。

### 5.3 按消息类型安排

| 用户输入 | 推荐节奏 |
|---|---|
| 明确问题或请求 | 首条先给实际答案；可选第二角色补充不同角度；答案未完成前不讲角色故事 |
| 普通分享 | 先回应分享中的重点；可选相关经历；最后留下观点或容易接住的话头 |
| 情绪表达 | 先承接情绪，减少抢答和建议；通常 1—2 个角色，停顿可以比平时更长 |
| 行动计划 | 先回应计划，再补充风险、鼓励或不同意见；避免三角色重复建议 |
| 征求观点 | 可形成 A 观点、B 温和反对、A 或 C 收尾的短讨论 |
| 错字或不明确输入 | 只由一个角色自然澄清，不集体围观 |
| 明确切换话题 | 旧轮次未发送内容全部取消，新话题立即成为焦点 |

## 6. 气泡长度与显示间隔

### 6.1 表达长度

- 大多数气泡只表达一个主要意思。
- 推荐 12—60 个汉字；确需解释的首答可更长，但应避免报告式长段落。
- 一段内容存在自然停顿、补充或情绪转折时才拆成两个气泡。
- 不能为了显得像真人而故意发送“嗯”“然后呢”等无信息气泡。

### 6.2 推荐显示间隔

以下时间从内容已经生成并通过校验后计算，不包含模型网络延迟：

| 情况 | 推荐间隔 |
|---|---:|
| 首个气泡 | 0.6—1.8 秒 |
| 同角色第二气泡 | 0.4—1.0 秒 |
| 切换到另一角色 | 0.9—2.5 秒 |
| 情绪较重或需要斟酌 | 在上述基础上增加 0.5—1.5 秒 |
| 明确的“又想到一点”可选补充 | 3—8 秒，且用户发言即取消 |

具体间隔应根据文字长度、情绪和角色表达速度计算并加入小幅随机扰动，不得长期固定为两个常量。等待时间上限必须以用户体验为先，不能用夸张延迟假装真人。

## 7. 如何把话题继续下去

一次回复不需要每次都以问题结尾。可用以下方式给用户留下参与入口：

- 提出一个具体而非审问式的问题；
- 分享一个相关但未讲完的经历；
- 表达一个可以同意或反对的观点；
- 给出两个可选择的方向；
- 让另一角色对上一条内容作出反应；
- 明确表示愿意继续听；
- 内容已经完整时自然结束。

为了防止“客服访谈感”，以问号结束的轮次建议长期保持在 20%—50%，不得每轮固定追问。

## 8. 角色故事的事实边界

角色故事必须标记内部来源类型：

| 类型 | 含义 | 规则 |
|---|---|---|
| `canon_backstory` | 角色合同中已经确定的背景故事 | 固定事实，修改需升角色合同版本 |
| `shared_history` | 用户和群角色真实发生过的群内经历 | 必须能追溯到消息或记忆记录 |
| `virtual_episode` | 角色虚拟生活中的受控日常片段 | 首次说出后写入故事账本，后续不得矛盾 |
| `hypothetical` | 想象、比喻或“如果是我”的假设 | 表达中必须能让用户理解它是假设 |
| `real_world_fact` | 位置、天气、新闻、交通、活动、POI 等 | 必须使用有效证据封装，不能由故事系统生成 |

产品持续标识群成员为 AI。角色不得声称拥有真实肉身、现实职业、现实住址或现实中刚完成某项活动；如产品使用虚拟生活设定，必须属于明确的角色世界并在内部记录为 `virtual_episode`。

## 9. 角色故事账本

每个已经说出口并准备复用的故事必须进入 `CharacterStoryLedger`：

```ts
interface CharacterStory {
  id: string;
  ownerId: string;
  type: 'canon_backstory' | 'shared_history' | 'virtual_episode' | 'hypothetical';
  title: string;
  summary: string;
  keyFacts: string[];
  relatedCharacterIds: string[];
  emotionalMeaning: string;
  canonStatus: 'fixed' | 'accepted' | 'temporary';
  createdAt: number;
  lastMentionedAt: number | null;
  mentionCount: number;
  sourceMessageIds: string[];
}
```

故事账本规则：

- 新虚拟片段首次输出前先做角色合同和既有故事冲突检查；
- 说出口后至少保存摘要、关键事实、人物关系和情绪意义；
- 再次提及时只能自然补充，不能改变关键事实；
- 同一故事默认 72 小时内不得主动重复，同类主题默认冷却 4 小时；
- 一次只披露与当前话题相关的一小部分；
- 普通修辞和一次性假设不必永久保存，但不得被当成固定经历召回；
- 删除相关聊天或记忆后，依赖该记录的故事应失效或降级为不可主动引用。

## 10. 角色自主交流机会

自主轮次必须由 `AutonomousConversationOpportunity` 产生，而不是由定时器直接生成内容：

```ts
interface AutonomousConversationOpportunity {
  id: string;
  source: 'character_story' | 'shared_memory' | 'unfinished_topic' | 'relationship' | 'world_evidence';
  initiatorId: string;
  topic: string;
  motive: string;
  importance: number;
  confidence: number;
  storyId: string | null;
  evidenceIds: string[];
  expiresAt: number;
}
```

时间只负责提供检查机会，不得成为唯一发言理由。

### 10.1 允许触发

- 当前环境自然唤起一段固定故事或真实群内共同经历；
- 用户留下了尚未结束且仍有关系价值的话题；
- 两个角色基于稳定关系对同一件事存在不同关注点；
- 某个角色有尚未过度披露、与当前群状态相关的故事片段；
- 有有效世界证据，并且角色之间确实存在值得讨论的不同反应；
- 关系状态发生了有事件依据的变化，需要一次自然修复或回应。

### 10.2 禁止触发

- 只是定时器到了；
- 只是角色“无聊”“饿了”或系统想制造活跃；
- 没有来源地随机编一段过去；
- 用户正在输入、刚刚发送新消息，或即时回应仍未完成；
- 同类故事或话题仍在冷却；
- 消息预算不足或连续 AI 气泡已达上限；
- 需要依靠未经证实的现实信息才能成立；
- 最近已经有角色自主轮次，继续说只会形成刷屏。

## 11. 自主轮次的结构与预算

推荐结构：

1. 发起角色用一个短气泡给出具体话头。
2. 第二角色必须回应其中的具体观点、情绪或故事细节。
3. 可由发起角色补充，或第三角色形成收尾。
4. 随后进入沉默，不自动开启新主题。

推荐默认值：

- 每个自主轮次 2—3 个气泡，硬上限 3。
- 同一角色作为自主发起者后默认冷却 90 分钟。
- 任意自主轮次之间默认至少间隔 30 分钟；有重大有效世界变化时可按原机会规则处理。
- 独立故事轮次只在用户连续安静约 45 秒后评估；未结束话题的延迟追聊按第 3.2 节执行，不占用 30 分钟的独立故事冷却。
- 没有合格机会时，3 小时 0 条消息是正确结果。
- 任意 3 小时未读目标 0—20，硬上限 30。
- 长期目标仍为约 70% 时间沉默、20% 偶尔交流、10% 短暂热闹。

以上冷却是推荐默认值，可以通过真实用户测试调整，但不得取消机会、预算和硬上限。

## 12. Director 的轮次计划

Director 不生成台词，应输出可解释的轮次计划：

```ts
interface ConversationBeat {
  speakerId: string;
  motive: 'answer' | 'acknowledge' | 'expand' | 'share_story' | 'react' | 'challenge' | 'support' | 'ask' | 'repair' | 'close';
  replyTarget: 'user' | string;
  required: boolean;
  maxBubbles: 1 | 2;
  storyId: string | null;
  delayProfile: 'quick' | 'normal' | 'thoughtful' | 'afterthought';
  stopAfter: boolean;
}

interface ConversationRoundPlan {
  trigger: 'user' | 'world' | 'autonomous';
  topicId: string;
  beats: ConversationBeat[];
  maxAiBubbles: 3;
  cancellable: boolean;
  expiresAt: number;
  reason: string;
}
```

规则：

- 首个用户轮次 Beat 必须以用户为目标；
- 后续 Beat 必须与用户或前一个 Beat 存在明确语义关系；
- `required=false` 的 Beat 在用户发言、过期、状态变化或预算不足时取消；
- 最后一个 Beat 已提出明确问题时通常 `stopAfter=true`，避免其他角色抢在用户前回答；
- 故事分享必须携带故事来源或故事候选 ID。

## 13. 模型输出与播放

V4.5 继续采用一次模型调用批量生成本轮内容，避免按角色进行三次模型调用。模型输出应按 Beat 生成，并允许一个角色回合包含两个气泡：

```ts
interface GeneratedCharacterTurn {
  speakerId: string;
  motive: string;
  replyTo: 'user' | string;
  bubbles: string[];
  storyUsage: {
    storyId: string | null;
    type: string | null;
    newCanonCandidate: boolean;
  };
}
```

播放层必须：

- 按气泡而不是整段文字显示；
- 根据 `delayProfile`、字数和角色速度计算间隔；
- 支持取消尚未播放的可选气泡；
- 不因 `typing=true` 禁止用户发送；
- 只显示当前真正准备发言的角色名称，不使用长期不变的通用假输入状态。

## 14. 验收标准

| 指标 | 目标 |
|---|---:|
| 用户明确意图的首条 AI 回复直接相关 | ≥ 90% |
| 后续角色接住前一条具体语义 | ≥ 80% |
| 用户在 AI 播放期间成功发送并抢占低优先级队列 | 100% |
| 同角色连续两个气泡具有真实补充关系 | ≥ 90% |
| 同角色连续三个气泡 | 0 |
| 合格场景中的相关故事分享占比 | 10%—30% |
| 与当前话题无关的角色故事 | 0 |
| 已入账故事关键事实矛盾 | 0 |
| 虚构用户共同经历 | 0 |
| 无证据现实事实断言 | 0 |
| 自主轮次第二条接住第一条具体内容 | ≥ 80% |
| 自主轮次超过 3 个连续 AI 气泡 | 0 |
| 每轮固定以问题结尾 | 0；长期问号结尾率建议 20%—50% |
| 无合格机会时的自主发言 | 0 |
| 任意 3 小时未读消息 | 0—20，硬上限 30 |

## 15. 当前实现差距

在实现本规范前，现有代码至少存在以下差距：

1. `DirectorDecision.maxMessages` 混合了角色数、角色回合数和气泡数。
2. 当前 Director 对多数用户消息倾向直接安排三个角色，缺少长期参与人数分布和可选 Beat。
3. 云函数提示词禁止同一角色连续两条，无法表达自然的补充气泡。
4. 云函数返回的是最终消息数组，没有发言动机、故事来源和可取消属性。
5. 前端在 `typing=true` 时禁止用户发送，用户无法打断角色队列。
6. 前端只使用固定 700/900 毫秒间隔，没有考虑字数、角色和情绪。
7. 当前没有角色故事账本，模型临时生成的过去无法检查或延续。
8. 当前没有角色自主交流机会类型和对应预算。

## 16. 推荐实现顺序

1. 先拆分 Bubble、Character Turn、Group Round，并允许用户打断队列。
2. 把 Director 改为输出带动机和可选性的 Beat 计划。
3. 调整模型输出结构，允许一个角色 1—2 个气泡并采用动态间隔。
4. 为当前三个角色补齐故事合同和首批固定故事种子。
5. 建立故事账本、冲突检查、披露次数和冷却。
6. 上线用户驱动的相关故事分享。
7. 最后开启受预算约束的角色自主轮次。
8. 按本规范和 `CHARACTER_EVALUATION_PROTOCOL.md` 执行回归评测。

## 17. 核心原则

角色不是等待用户调用的回答函数，也不是在后台随机编故事的消息机器人。角色应当拥有可追溯的过去、当前状态和关系动机；有话可说时参与，用户开口时让出焦点，没有新增价值时保持安静。
